# Player profiles and practice PvP — GDD addendum

## Implemented on development

- Click a nickname in any leaderboard to inspect the player's latest published equipment, attributes, derived combat stats, and numeric set bonuses. Existing rarity frames and asset mappings are reused.
- Find any registered player by their **full nickname**, case-insensitive, using the nickname reservation document. Search is not limited to the top 50. Prefix search is not included.
- Public snapshots contain equipment and dungeon level only. Inventory, Gold, private saves and Google account data are not exposed. Only the owner can publish equipment; signed-in players can read individual public snapshots. Players need to sign in and sync with this release before their equipment appears.
- `Attack · Practice` runs a deterministic, cosmetic test duel against the last shared loadout. No Gold transfer, loot, progression or permanent damage occurs. Self-attacks and attacks during an expedition are blocked.
- Practice uses the existing stat/set formulas, generated by `npm run build:pvp`; `npm test` rejects a stale generated module. It supports Sword/Shield, Mace/Shield, Two-Handed, Daggers/Off-Hand Dagger, Staff/Orb and Wand/Orb. Arena cadence is capped at five attacks/second, matches time out at 120 seconds with a draw. Block, criticals, mana, passive off-hands, damage over time, Slow, Sunder, barriers and healing have bounded practice rules. This is a separate **practice** battle resolver, not proof of a PvE or competitive victory.
- Existing Two-Handed saves, Off-Hand Dagger, PvE calculations and save data are unchanged.

## Not activated: stealing Gold

The owner selected stealing a small part of the defender's Gold and confirmed that Firebase uses **Spark**. There is no trusted economy or combat backend in this project. Firebase Cloud Functions deployment requires Blaze; an independently hosted authenticated backend is another option. No billing upgrade or backend deployment has been performed.

Proposed limits, represented by a pure preview function, not actual transfers:

- 1% of the defender's current server-owned Gold, rounded down.
- Maximum 20 Gold per victory, 100 gained per attacker/day, 50 lost per defender/day (UTC day).
- The same opponent cannot yield a reward again for 24 hours. Never attack yourself.
- No equipment loss; no fees or Gold loss on defeat/draw. No reward from empty/very small balances.

Before enabling theft:

1. Establish server-owned equipment and balances. Current cloud saves and public gear can be edited by their owner; simply moving the practice calculation to a function would still allow forged builds. Imported saves must not silently become trusted assets.
2. Authenticate both participants by server-owned profile IDs; derive attacker UID from the token. Accept only defender ID and an idempotency key, never a claimed winner or reward.
3. Reserve a bounded match/cooldown, snapshot eligible server-owned equipment and compute the result server-side with versioned rules and a server seed. Record authoritative timestamps. Reject concurrent/ineligible matches.
4. In one transaction, debit defender, credit attacker and update both daily budgets, pair cooldown and immutable match receipt. Apply `min(floor(defenderGold * .01),20,remainingGain,remainingLoss)` against balances read inside that transaction. Never permit negative balances or replay rewards. Include anti-collusion/rate limits before public launch.
5. Route all currency changes through the ledger, including PvE awards, purchases and saves. An old browser save must not restore stolen Gold or erase newly earned Gold; the current revisioned client-owned save is insufficient authority for this.
6. Test duplicate requests, simultaneous attacks, UTC rollover, exhausted budgets, same-account attacks, forged loadouts, stale saves, offline clients and deleted accounts. Obtain explicit approval for any paid infrastructure and deployment.

## Deployment prerequisite and tests

`firestore.rules` includes the new `publicLoadouts/{uid}` access rules. **They have not been deployed.** Existing Rules will reject snapshot publication/inspection until the owner deploys the reviewed Rules. Core cloud save/result sync remains separate from public-loadout publication so a profile-sharing failure does not cancel a save.

- Game/save/profile regression suites pass.
- Eight model/adapter tests pass, including all 36 combinations of six representative builds, deterministic results, unchanged inputs, zero practice reward, Two-Handed synergy counting and theft-preview boundaries.
- Mocked Firebase browser checks pass at 1440, 390 and 320 pixels: leaderboard profile, stats/sets/equipment, search outside top rankings, failed search, practice log, self-attack rejection and unchanged equipment/currency.
- New emulator Rule cases cover signed-in read, unauthorized writes, private fields, size limits and denied client transfers. They are prepared but **not executed**; the emulator download was previously blocked in this environment.
- Live profile sharing and any paid/competitive backend remain untested and undeployed. No main merge or Pages publication.
